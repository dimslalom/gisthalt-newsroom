Consequences

Three things your answers changed

Good news: the four-week Instagram wall is gone

Meta's app review only gates the Graph API. Browser automation needs no app, no Business account, no linked Facebook Page, and no review. That removes the single longest blocker in the original plan and pulls first-post from roughly eight weeks to four.

Keep the Meta app on the shelf as the upgrade path. When an account earns enough to justify $11 a month on X and the reliability of official endpoints, you switch the publisher adapter and nothing else changes. That is exactly why the publisher is its own layer.

Bad news: new accounts plus automation is the riskiest possible combination

Automated posting is against the terms of all four platforms. An account can be suspended with no appeal, and a brand-new account with no usage history that starts posting on a schedule is the easiest possible pattern to spot. This is a real cost of the path you chose, not a footnote.

It is survivable, and the warm-up schedule below is how. The non-negotiables: one browser profile per account, never shared; always your home IP; jittered human pacing; no bulk-follow or DM automation ever; and a full local archive of every post so a lost account can be rebuilt in a day rather than from nothing.

Windows splits the runtime in two, and fonts are the trap

Docker Desktop runs Linux containers under WSL2. That is right for Postgres, the workers and the dashboard, and right for the renderer, where a fixed Linux container with pinned fonts gives byte-identical output every time. It is wrong for the publisher, which needs a real consumer browser fingerprint, a persistent profile, and a window you can watch when a login challenge appears.

So: pipeline in Docker, publisher as a native Windows Node process driving real Chrome. And never preview templates in Windows Chrome. Windows and Linux rasterise type differently, so a layout that fits in your preview can overflow in the render. The dashboard must preview by calling the container's renderer, not by displaying the HTML locally.

Topology on one Windows machine

Docker / WSL2
Pipeline
  • postgres single source of truth, also the job queue via graphile-worker

  • extractor Gemini Flash-Lite with the quote requirement
  • gate the five deterministic rules

Native Windows
Publisher agent
  • Node process launched by Task Scheduler at boot
  • Playwright driving real Chrome, not bundled Chromium
  • One userDataDir per account per platform, twelve in total
  • Polls Postgres for ready-to-publish jobs
  • Headed, on a visible desktop, so you can take over a login challenge
  • Reports session health back to #alerts every hour
Windows setup
Uptime chores
  • Disable sleep and hibernate, including on the display power plan
  • Docker Desktop set to start at login, WSL2 memory capped in .wslconfig
  • Windows Update active hours set wide, auto-restart deferred
  • Auto-login so a reboot returns to a desktop session, since headed Chrome needs one
  • A watchdog that pings #alerts if any container or the agent is down two minutes

The renderer writes PNGs to a shared volume the publisher agent can read. No object storage needed, because browser automation uploads a local file rather than fetching a public URL. That removes the Cloudflare R2 dependency the API path required.

Dashboard

Four screens, and the template lab is the important one

ScreenWhat it doesWhy it exists
Template lab Four dropdowns: fixture, archetype, layout, skin. Accent modules as toggles. Renders through the container renderer and shows the real PNG at true size and at feed size. A "render all variants" button produces the full matrix for one fixture. This is where you design. Every layout must be provable against every fixture before it can ship, and looking at one render at a time is how broken edge cases reach production.
Contact sheet Sixty posts from real historical data in a grid, plus a simulated profile grid showing the last nine as Instagram would arrange them. Coherence and variety are properties of a set, not of a single image. The profile grid catches the specific failure where nine good posts look identical stacked together.
Review queue The same items Discord shows, with a wider editing surface: caption editing with character counts per platform, variant reshuffle, source links, extracted claim and its supporting quote. Discord is for approving in fifteen seconds on a phone. This is for the times you want to actually work on something.
Ops Source health with last-success timestamps, queue depth, publish log with per-platform latency, session health for all twelve browser profiles, and the day's post count per account against target. Sessions dying silently is the single most likely failure mode of the path you chose. It needs a screen, not just an alert.
Design QA

The fixture library, and the guards that make layouts survive it

Every fixture is a committed JSON file. Every layout renders against every fixture in CI, compared to a golden PNG with pixelmatch. A layout that has not passed the full fixture set cannot be selected by the composer, enforced in code rather than by discipline.

Fixtures

title-overflow
Four times the expected headline length. Plus the longest real names in each vertical: constructor full legal names, Korean and Japanese VCT org names, film titles with subtitles and colons.
title-underflow
A one-word headline. Under-fill breaks composition as badly as overflow, and it is the case nobody tests. A layout with a giant empty middle is a bug.
image-missing
No image, a 404, and a 120px thumbnail. Each must fall back to a typography-only variant rather than render a grey box. Every archetype therefore needs at least one no-image layout.
image-lowcontrast
A white sky where white text goes, and a dark frame where dark text goes. The contrast guard must trigger and be visibly correct, not just technically pass.
image-busy
High-detail photo with no quiet corner. Forces the logo placer into its fallback, which is a solid strip rather than a corner.
image-wrongratio
Ultra-wide and ultra-tall sources. Smart crop must keep the subject, and the result must still be 4:5 because Instagram crops a carousel to slide one regardless.
data-missing
DNS, DNF, no gap, no lap count, a release date of "TBA". Missing values render as an em-free dash, never as blank space or the string "undefined".
data-extremes
A 4-row classification and a 22-row one. Plus gap values spanning +0.002 to +1 LAP, which have wildly different widths in a tabular column.
colour-clash
A near-white entity colour on the light skin, and a near-black one on the dark skin. The entity table's contrast pairing must kick in and swap the text colour.
diacritics
Hulkenberg, Perez, Norrkoping, Nurburgring, plus Hangul and Kana org names. Catches missing glyphs in the pinned font set, which is exactly what silently falls back to a different typeface.

Guards

Four pure functions in packages/design, unit-tested independently of any layout. They are what turn "handle the edge case" from a per-layout chore into a property of the system.

GuardHow it worksFailure behaviour
fitText()Binary-searches font size between a floor and a ceiling using the browser's own measurement, then clamps to a line count, then ellipsises. Never a fixed size and a hope.Below the floor, switches to a longer-headline layout variant.
pickTextTreatment()Samples mean luminance and standard deviation of the image region under the text, via sharp. Returns a scrim opacity and a text colour. Deterministic, so it is testable without rendering.If variance is too high for any scrim, returns "no text over image" and the layout moves the text to a solid panel.
pickLogoCorner()Scores edge density in each of the four corners, lowest wins, with a fixed tie-break order so placement stays consistent across a series rather than jumping around.If every corner scores busy, returns "strip" and the logo goes in a solid bar.
assertContrast()Runs a WCAG ratio check on every text-on-background pair the layout actually resolved, after skin and entity colour injection.Fails the render. An unreadable post is worse than a missed post, so it goes to review rather than out.
 Golden-image tests catch visual drift. These guards catch data the golden images never contained. You need both.
Operations

Warm-up and volume

Consistency is the aim, so the schedule matters more than the peak. But a brand-new account that starts at twelve posts a day is a brand-new account that gets suspended. Ramp it.

Weeks 1-2
0
Automated posts. Post by hand from your phone, follow people, comment, scroll. You are building a usage history.
Week 3
2-3
First automated posts, and only during hours you would plausibly be awake.
Week 4
4-6
Still mixing in manual posts and manual engagement so the pattern is not purely mechanical.
Weeks 5-6
6-9
Live event coverage switched on, which naturally clusters posts around real-world timing.
Steady, quiet day
5-7
The floor. Consistency lives here, not on race weekends.
Steady, event day
12-16
Race Sunday or a VCT match day. Clustering is fine because the events are real.

Roughly 250 posts a month per account at steady state. Two pacing rules the publisher must enforce in code, not in a cron expression: jitter every interval by a random 0 to 9 minutes so the cadence is never exact, and never post between 01:00 and 06:00 local unless a real event is running, because a 3am post with no event behind it is a pure bot signal.

What I would do first

Three things, in this order

  1. Today, before qualifying: a throwaway script that polls OpenF1 for the qualifying session and logs a timestamp the moment results appear. Ten minutes of work, and it answers the only question that determines whether the whole latency promise is real.
  2. Today or tomorrow: pick the F1 brand name and claim the handle on all four platforms. The warm-up clock is the longest pole left in the plan, and it costs nothing to start it before any code exists.
  3. Then: scaffold the monorepo and the Docker Compose file, so phase 2 has somewhere to land.

One open question I did not decide for you: whether the three brands share a visual family (a recognisable house style across all three accounts) or are fully independent identities. Sharing means one token system and far less design work; independence means each account can look native to its own fandom, which matters more than it sounds when the audiences barely overlap.
